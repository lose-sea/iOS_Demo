# 三级缓存（Three-Level Cache）讲解

> 面向本项目（Spotify iOS Demo · Objective-C）整理。
> 目标：先搞懂「三级缓存是什么 / 为什么 / 怎么做」，再决定怎么接进 `NeteaseService`。
> 本文只讲概念与方案设计，不含最终实现代码。

---

## 1. 为什么需要缓存

现在的状况：**每一次展示数据都真的发一次网络请求**。

```
打开首页      → 5 个请求（榜单 / 热歌榜 / 艺人 / 电台 / 专辑）
点进歌单      → 1 个请求
播一首歌      → 1 个请求（取播放地址）
进详情页      → 1 个请求（取歌词）
```

在本地 `localhost:3000` 上感觉很快，但真机上就是公网请求 + 用户流量。缓存解决四件事：

| 收益 | 说明 |
| --- | --- |
| 快 | 内存命中是微秒级，磁盘是毫秒级，网络是百毫秒级起 |
| 省流量 | 重复内容不再重复下载（封面图尤其明显） |
| 离线可用 | 弱网/断网时页面仍有内容，而不是一片空白 |
| 降服务端压力 | 对真实线上服务很重要 |

代价也要认清：**数据可能变旧（一致性问题）**、占存储空间、代码复杂度上升。所以缓存不是「全都缓存」，而是「按数据的变化频率分级缓存」。

---

## 2. 三级是哪三级

核心思想一句话：**离 CPU 越近的介质，越快、越小、越容易丢失**。

| 级别 | 存在哪 | 速度 | 容量 | 生命周期 | 本项目可用实现 |
| --- | --- | --- | --- | --- | --- |
| L1 内存 | App 进程内存 | 最快（微秒级） | 小（几十 MB） | App 被杀 / 内存警告即失效 | `NSCache` |
| L2 磁盘 | 沙盒 `Library/Caches` | 快（毫秒级） | 大（几百 MB） | 重启 App 仍在；系统空间不足时**可能被清掉** | 文件 / `YYCache` / WCDB |
| L3 网络 | 远端服务器（含 `NSURLCache` 这层临时缓存） | 慢（百毫秒~秒） | 无限 | 由服务端 `Cache-Control` 决定 | `NSURLSession` + `NSURLCache` |

```
     快 ↑                                          ↓ 慢
  ┌──────────┐      ┌──────────┐      ┌──────────┐
  │ L1 内存   │ miss │ L2 磁盘   │ miss │ L3 网络   │
  │ NSCache  │ ───→ │ 沙盒文件   │ ───→ │ 接口请求  │
  └──────────┘      └──────────┘      └──────────┘
        ↑                  ↑                  │
        └──────────────────┴──────────────────┘
                    拿到数据后逐级回写
```

> 有的资料把 `NSURLCache` 单独算一级（内存缓存 / 磁盘缓存 / 网络缓存 = 三级），有的按「内存 / 本地 / 服务端」分。本质一样，不必纠结名词，关键是**分层的思想**。

## 3. 读取流程：Cache-Aside（旁路缓存，最常用）

这是业界最通用的模式，逻辑很简单：**先查缓存，命中就直接用；没命中才请求网络，拿到后回写缓存**。

```
请求数据(key)
   │
   ├─→ 查 L1 内存 ── 命中 ─→ 直接返回 ✔
   │
   └─→ 未命中 → 查 L2 磁盘 ── 命中 ─→ 回写 L1 → 返回 ✔
                    │
                    未命中 → 发网络请求 ── 成功 ─→ 回写 L2 + L1 → 返回 ✔
```

几个术语：

- **命中（hit）/ 未命中（miss）**：在某一级里找到了 / 没找到
- **回写**：从慢的层级拿到数据后，往快的层级再存一份，下次就快了
- **命中率**：`命中次数 / 总请求次数`，衡量缓存做得好不好
- **预热**：提前把大概率要用的数据放进缓存（比如启动时预取首页数据）

一个实用变体是 **stale-while-revalidate（先给旧的，后台刷新）**：磁盘里有过期数据也先展示，同时后台偷偷刷新，刷新完再刷新 UI。用户体验最好（永远不空白），代价是代码复杂，初版可以先不做。

## 4. 写入与失效：缓存最难的部分

「存进去」很简单，「什么时候该扔掉」才是重点：

| 策略 | 做法 | 适用 |
| --- | --- | --- |
| TTL 过期 | 每条数据记一个过期时间，超了就当没有 | 几乎所有接口数据 |
| 协商缓存 | 带 `ETag` / `Last-Modified` 问服务端，没变则返回 304 不传内容 | 服务端支持时最省流量 |
| 主动失效 | 数据变了就手动删掉对应 key（如取消收藏后清掉「我的喜欢」） | 本地状态变化 |
| 容量淘汰 | 超过上限就删最旧的 | 防止无限增长 |

### 淘汰算法

- **LRU（Least Recently Used，最近最少使用）**：满了先删最久没被访问的。最常用，符合直觉。
- **LFU（Least Frequently Used）**：先删访问次数最少的。
- **FIFO**：先删最早进来的，简单但不精准。

iOS 的 `NSCache` 内部就自带淘汰（且会在内存紧张时自动清理），**但它的淘汰策略不公开、也不保证时机**，所以仍然要自己监听内存警告做兜底清理。

---

## 4.5 LRU 详解：它和三级缓存是什么关系

**一句话：LRU 不是和三级缓存并列的东西，而是每一级「满了之后怎么扔」的策略。**

TTL 管「数据是不是旧了」，LRU 管「空间够不够放」，两者**互补、同时生效**，不是二选一：

| 维度 | 解决的问题 | 例子 |
| --- | --- | --- |
| TTL | 数据**是不是旧了** | 榜单缓存 1 小时，超时就当没有 |
| LRU | 空间**够不够放** | 就算没过期，缓存满了也要挤掉最冷门的 |

一条缓存同时受两个规则约束：过期 → 失效；没过期但空间不够 → 被 LRU 淘汰。

### 原理：局部性原理

刚被访问过的数据，接下来大概率还会被访问；很久没碰的，大概率也不会再碰。所以容量不足时，**优先淘汰最久没被访问的**。

### 数据结构：哈希表 + 双向链表

要做到「查找」和「调整顺序」都是 O(1)，标准解法是这两个结构组合：

```
哈希表（O(1) 找到节点）
  key → node

双向链表（维护访问顺序，O(1) 移动 / 删除）
  MRU ── A ── B ── C ── D ── LRU
  头部（最近用过）            尾部（下次淘汰它）
```

| 操作 | 做法 | 复杂度 |
| --- | --- | --- |
| `get(key)` | 哈希表找到节点 → 移到链表头部（表示"刚用过"） | O(1) |
| `put(key, value)` 已存在 | 更新值 → 移到头部 | O(1) |
| `put` 不存在 | 插到头部 → 超过容量就**删掉尾部节点** | O(1) |

**为什么必须是双向链表**：删除任意节点需要它的前驱指针，单向链表做不到 O(1) 删除（这是 LRU 最经典的考点）。

### 在三级缓存的每一层怎么用

**L1 内存**：命中或写入时都要「移到头部」，满了从尾部删。
`NSCache` 内部就是类似 LRU 的淘汰（策略不公开、时机不保证），可通过 `countLimit` / `totalCostLimit` 设上限，但不严格。

**L2 磁盘**：磁盘**没有任何自动淘汰机制**，写满就是写满，必须自己按 LRU 清理。
关键细节：**读命中时一定要更新访问时间**，否则 LRU 退化成 FIFO（变成只按写入时间排）。
实现上维护一份索引（`key → {文件大小, 最后访问时间, 文件名}`）比每次遍历 `stat` 文件快得多。

**L3 网络**：不存在容量问题，不涉及 LRU。

### 一个容易忽略的点：两层淘汰代价完全不同

```
L1 内存 LRU 淘汰 → 只是从内存消失，磁盘里还有 → 下次从磁盘恢复，代价很小
L2 磁盘 LRU 淘汰 → 真的没了 → 下次必须重新走网络
```

所以**磁盘容量要设得大方**（如 100~200 MB），内存可以小（几十 MB）。内存淘汰频繁点无所谓，**磁盘淘汰才真的伤性能**。

### 在本项目里的表现

- 用户在「首页 ↔ 歌单 ↔ 播放详情」之间反复跳：热歌榜、歌单详情一直留在 LRU 头部 → 秒开、不发请求
- 用户搜了十几个关键词：早期的搜索结果自然沉到尾部被淘汰，不需要手动清理
- 歌词命中一次就移到头部，热门歌的歌词长期留存，冷门的慢慢被挤掉
- ⚠️ **收藏状态这类真实用户数据不能进 LRU**（否则会被淘汰掉），必须走持久化

### 取舍建议

- **内存层**：初版直接用 `NSCache`，够用、省事、线程安全
- **磁盘层**：**必须自己写 LRU 清理** —— 这是唯一没有现成轮子的一层
- 想精确控制（"最多缓存 100 条"）或要讲清原理，再自己实现一遍「哈希 + 双向链表」的 LRU

## 5. iOS 上现成的轮子

| 方案 | 提供哪一级 | 说明 |
| --- | --- | --- |
| `NSCache` | L1 内存 | 线程安全、自动淘汰、不会像 `NSMutableDictionary` 那样把内存撑爆 |
| `NSURLCache` | L1 + L2（网络层自带） | `NSURLSession` 默认就走它，是否缓存取决于服务端返回的 `Cache-Control` |
| `SDWebImage` | **L1 + L2 + L3 全包** | 图片加载的标准三级缓存，本项目已在用 |
| `YYCache` / `PINCache` | L1 + L2 | 内存+磁盘一体化，支持数量/大小/年龄限制、LRU |
| WCDB / FMDB | L2 | 结构化数据（项目里已经引入了 WCDB） |

### 两个必须先知道的点

**1）本项目里图片其实早就有了三级缓存。**

`sp_setImageWithSource:` → `sd_setImageWithURL:` 内部就是：

```
内存缓存(SDImageCache) → 磁盘缓存(沙盒) → 网络下载 → 回写磁盘+内存
```

所以**封面图不用你做任何事**，学长说的三级缓存通常指的是**接口数据（JSON）**那一块。

**2）别自己用 `NSMutableDictionary` 当内存缓存。**

- 不线程安全：多线程读写会崩（本项目网络回调都在主线程，但磁盘读写会开子线程，很容易踩到）
- 不响应内存警告：App 内存涨上去下不来，最终被系统杀掉
- `NSCache` 两个问题都解决了，直接用它

## 6. 本项目里，各数据该怎么缓存（重点）

缓存设计的核心是**按「变化频率 + 出错代价」分级**。结合你现在用的这几个接口：

| 数据 | 接口 | 建议 | TTL 建议 | 理由 |
| --- | --- | --- | --- | --- |
| **封面图片** | — | 内存 + 磁盘 | 交给 SDWebImage | 已经自带三级缓存，不用改 |
| **歌词** | `/lyric` | 内存 + 磁盘 | 长期（几天 / 不过期） | 一首歌的歌词基本不变 |
| **歌单 / 榜单详情** | `/playlist/detail` | 内存 + 磁盘 | 内存 5 分钟，磁盘 1 小时 | 榜单更新频率一般是小时级 |
| **首页分区** | `/toplist`、`/top/artists`、`/album/new` | 内存 + 磁盘 | 磁盘 1 小时 | 同上 |
| **搜索结果** | `/search` | 内存（磁盘可选） | 1~3 分钟 | 用户会反复改关键词，缓存太旧会「搜出新东西却给旧的」 |
| **播放地址** | `/song/url` | **不缓存，或只内存缓存极短时间** | ≤ 1~2 分钟 | ⚠️ **本项目最大的坑，见下** |
| **收藏状态** | 本地 | 不是缓存 | — | 这是真实用户数据，走 `UserModel` / 持久化，不属于接口缓存 |

### ⚠️ 播放地址千万别久缓存

网易的播放地址是**带时效的**（URL 里带时间戳和签名参数，类似 `/20261004014337/...mp3?vuutv=...`）。缓存久了再拿出来播，会直接播不出来或 403。

所以：**播放地址要么不缓存，要么只在内存里缓存一两分钟**——同一次播放会话里重复切歌有用，落盘毫无意义。

## 7. 怎么接进现在的 `NeteaseService`（方案，不是实现）

现在的调用链是：

```
ViewController → NeteaseService → NetworkManager(AFNetworking) → 本地 Node 服务
```

加缓存的位置建议放在 **`NeteaseService` 和 `NetworkManager` 之间**，新增一个 `SPCacheManager`，这样所有接口自动受益，ViewController 完全不用改：

```
ViewController → NeteaseService → SPCacheManager ──命中──→ 直接返回
                                        │
                                        miss
                                        ↓
                                  NetworkManager → 网络 → 回写缓存
```

### 设计要点

**① 缓存 key**

用**完整的请求 URL（含参数）**当 key，例如 `http://localhost:3000/search?keywords=晴天&limit=30`。
两个关键词不同的搜索不能共用一份缓存，所以参数必须进 key。
落盘时把 key 做一次 MD5 当文件名（URL 里的 `/`、中文、`?` 不适合直接当文件名）。

**② 存原始数据还是模型？**

建议**存接口返回的原始 JSON（NSData）**，不要存 `Song` 模型：

- 模型会随版本演进，字段改了旧缓存解不出来，容易崩
- 存 JSON，永远用当前的 `YYModel` 规则解析，最稳（这点和「别缓存 Model」是业界通用建议）

**③ 目录选 `Library/Caches` 而不是 `Documents`**

| 目录 | 会被 iTunes/iCloud 备份 | 系统空间不足时 |
| --- | --- | --- |
| `Documents` | ✅ 会 | 不动 |
| `Library/Caches` | ❌ 不会 | **会被清掉** |

缓存就该放 `Caches`：不备份、不用向用户解释、系统清理也不影响功能。

**④ 过期判定**

写一个小的包装结构一起存：

```objc
@interface SPCacheItem : NSObject <NSCoding>
@property (nonatomic, strong) NSData *data;        // 原始 JSON
@property (nonatomic, assign) NSTimeInterval savedAt;  // 存入时间戳
@end
```

读出来先判断 `now - savedAt > TTL` 就当没命中（简单可靠；也可以用文件修改时间，省一层）。

**⑤ 线程与清理**

- 磁盘读写放**串行队列**（子线程），结果回主线程再回调
- 监听 `UIApplicationDidReceiveMemoryWarningNotification` → 清空 `NSCache`
- 给磁盘缓存设一个总大小上限（如 100 MB），超了按「最后访问时间」从旧到新删
- **只缓存 GET、只缓存成功的响应**（失败/空数据不要写进缓存，否则会一直读到空）

## 8. 常见坑清单

1. **key 没带参数** → 搜「晴天」和搜「夜曲」返回同一份结果。
2. **播放地址缓存太久** → 播不出来（本项目最危险的一条）。
3. **磁盘无限增长** → 必须设上限 + 定期清理，否则用户存储空间被吃光。
4. **缓存了失败响应** → 服务挂一次，之后一直读到空，看起来像「接口坏了」。
5. **多线程竞争** → 用 `NSCache`（本身线程安全）+ 磁盘串行队列。
6. **把用户数据当缓存** → 收藏、创建的歌单是真实数据，不能因为「缓存过期」而消失，要走持久化。
7. **内存警告不处理** → App 被系统杀掉。
8. **以为 `Caches` 永远在** → 系统空间不足会清，代码要能容忍缓存不存在（有这个容错就是合格的缓存设计）。

### 三个延伸概念（了解即可）

- **缓存穿透**：查一个根本不存在的数据，缓存永远不命中，请求全打到服务端 → 空结果也要短期缓存。
- **缓存击穿**：某个热点 key 刚好过期，瞬间大量请求同时打穿到服务端 → 加互斥锁/单飞（只让一个请求去刷新）。
- **缓存雪崩**：大批 key 在同一时刻集体过期 → TTL 加随机抖动，别设成同一个值。

本项目是单机 Demo，这三个暂时不会遇到，知道名词就行。

## 9. 做完怎么验证

1. **断网测试（最有效）**：关掉 `node app.js`，重新打开 App → 首页/歌单/歌词应当**还有内容**（说明磁盘缓存生效）。
2. **命中率日志**：在 `SPCacheManager` 里打 `hit / miss`，正常用一段时间后命中率应该明显上升。
3. **看沙盒文件**：Xcode → Devices and Simulators → 下载容器，或用 `NSHomeDirectory()` 打日志看 `Library/Caches` 下文件大小与数量。
4. **重启 App 计时**：第二次打开首页应该明显快于第一次（磁盘命中）。

## 10. 名词速查

| 名词 | 含义 |
| --- | --- |
| TTL | Time To Live，缓存存活时间，超了就过期 |
| LRU / LFU | 最近最少使用 / 最不经常使用（淘汰算法） |
| Cache-Aside | 旁路缓存：先查缓存，miss 再查库/网络并回写 |
| 命中率 | 命中次数 ÷ 总请求次数 |
| 回写 | 从慢层拿到数据后写入快层 |
| 预热 | 提前把数据放进缓存 |
| 304 / ETag | 协商缓存：服务端说「没变」，就不用重新传内容 |
| 雪崩 / 击穿 / 穿透 | 三种典型的缓存失效故障（见第 8 节） |
